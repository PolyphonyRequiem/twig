# Twig architecture — wayfinder map

## Destination
A twig codebase whose architecture matches its stated ideology — four experiences (rich CLI, script CLI, MCP-as-LLM-toolkit, TUI) over deep shared modules — with a persistence model chosen on evidence, and documentation that is true. Reached when every ticket below is closed and nothing structural is left to decide.

**Scope note (2026-07-26):** this map's destination is *decisions*, not shipped work. A
second map with the destination "twig 1.0 shipped" is chartered separately in issue #282
and deliberately deferred — a different destination means a NEW map, not a child of this
one. This map does not spawn sub-maps: work that cannot yet be phrased sharply belongs in
**Not yet specified** below and graduates into tickets as the frontier reaches it.

- VOCABULARY CHANGED (0001): `Workspace` is retired in favour of **Connection** (one {org}/{project} ADO endpoint) and **Bench** (a named, switchable set of work items). `Sprig` is RESERVED for a future planning-over-seeds mode. See `CONTEXT.md` §4.

## Decisions so far

- 0008: all six registration touch points (3 CLI, 3 MCP) are now guarded by build-time completeness tests rather than by hand — including constructor-level assertions, because .NET DI's greediest-satisfiable-constructor rule makes a bare resolution test pass on a degraded path. The guards found a live bug: `twig save` was dispatching to an unregistered `SaveCommand`.

- [What is twig for?](tickets/0001-what-is-twig-for.md) — A single-user local tool each dev runs independently; the shared substrate is ADO, never twig. The cache is disposable, the PENDING SET is the only thing twig owns, and it needs its own lifecycle: selective push per item, forced parent-before-child sequencing, push-and-recover with durable intent recorded BEFORE the ADO call, interactive conflict resolution for humans and warn-and-advise for agents/scripts.

- [MCP toolkit scenarios and tool granularity](tickets/0012-mcp-toolkit-scenarios.md) — **MCP is FROZEN, not cut.** No new tools, no CLI↔MCP parity work; new agent capability goes through the script CLI first, and only a demonstrated scripting gap justifies a tool. Existing tools keep working. Backed by external evidence: the industry is actively leaving 1:1 proxying (GitHub 25→7 tools, Sentry advertises 9 of 48, Notion sunsetting its generated proxy), selection measurably degrades past 30–50 tools, and twig's 41 sit in that band. Scenario enumeration deferred with the evidence preserved.

- [Four surfaces, one seam?](tickets/0002-four-surfaces-one-seam.md) — **Three surfaces at one CAPABILITY seam, not four adapters at one render seam.** `Twig.RenderTree` has ONE adapter at the surface seam (its four renderers are `--format` values on the CLI) and is presentational, so it is scoped down to the CLI's format layer, not promoted. The real seam already exists and is already deep: the six mutation workflows in `Twig.Infrastructure/Services/Mutation/`, each with exactly two adapters (a CLI command and MCP's `MutationTools`), whose `Validate` → *(surface interjects if it can)* → `Execute` → match-the-outcome-union shape encodes INTERACTIVITY — the axis that actually varies. Reads never got it, and MCP's 34-property `WorkspaceContext` is the negative space where the read seam should be. Read workflows take ONE method, and REACH becomes an outcome case (`NotCached`), not a fetch policy buried in shared code — which puts the sync boundary back in the surface where 0001 §5 says the user owns it. Surfaces are counted by interaction model, not audience: CLI (experiences 1+2), TUI, MCP.
- [Seed identity model](tickets/0003-seed-identity-model.md) — **A seed's identity becomes a durable `StagedIdentity` minted at creation; the negative integer is demoted to a display alias.** Options (a) and (b) are rejected as a class: both are allocators, and every allocator needs a durable floor twig has nowhere to keep. (b) already shipped in #285, but it moved correctness onto the assumption that `publish_id_map` is permanent — and `DropAllTables` drops it on any `SchemaVersion` bump, while `init --force` deletes the DB, so #280 recurs through a different door. Per 0001 §1 that map is durable provenance sitting in the disposable mirror. The allocator also depends on five call sites each remembering to `Initialize` first — the `SaveCommand` failure shape from 0008. A generated identity has no preamble to forget: `ISeedIdCounter` and `GetMinSeedIdAsync` both delete cleanly, and the pre-ADO intent record 0001 §4 requires finally has a key that survives a cache wipe. Decision only; 0005 owns the schema work.
- [Does reconciliation exist?](tickets/0004-does-reconciliation-exist.md) — **Reconciliation becomes a named module owning staged → published → reconciled → invalidated.** Today the decision "when do local and remote meet" is nobody's: five independent opinions (`SyncCoordinator:51` staleness, `RefreshOrchestrator:74-91` plus an unguarded `force` bypass, `HydrateAncestorsAsync:104`, `PendingChangeFlusher:142-145`), the FK ordering rule enforced only by four XML doc comments, and `IPendingChangeStore?` nullable with legacy overloads at three sites — 0003's five-call-site argument at larger scale. `ConflictResolver:36` is already deep and simply unreachable from the paths that matter; the module exists to make it the default. **Unit is the pending set, per Connection — a Bench is a view, never a sync unit.** **Staleness-triggered fetch is removed, not relocated**: reads are cache-only and return `Stale(lastSyncedAt)` as an outcome each surface renders, per 0002's REACH-is-an-outcome ruling; `--no-refresh` is deleted and refresh becomes opt-in `--refresh`. The durable intent record is 0003's, keyed by `StagedIdentity` — not a second one. 0004 owns the root cause of #268/#269/#270/#271. Decision only; 0005 owns persistence, 0006 the baseline revision.

- [Split the store by durability class](tickets/0013-split-store-by-durability-class.md) — **Built.** `pending.db` is ATTACHed as schema `pending` and holds `pending_changes`, `publish_id_map` and `seed_links`; it is never dropped, and is versioned independently by `PRAGMA pending.user_version` over an additive migration ledger — twig's first migration path, and one it can never take back. `twig.db` keeps drop-and-recreate for what ADO can rebuild. The FK behind #268/#269/#270/#271 is now UNEXPRESSIBLE (two files cannot declare one), and #280 closes as a class since `publish_id_map` sits where a `SchemaVersion` bump cannot reach it. Two implementation facts later tickets depend on: SQLite resolves unqualified table names across attached schemas, so NO repository SQL changed; and the durable path is derived inside the constructor, so all three construction sites and ~60 test sites needed zero changes — there is no fourth place to forget. The clean-break guard found a live #271: `init --force` warned “pending changes will be lost” and deleted the DB anyway; it now refuses (exit 1) and never deletes `pending.db`. A second bug — an empty legacy `main.pending_changes` shadowing the durable table and silently taking the writes — was caught by an existing test and fixed. 7,383 → 7,389 tests, exit 0 on all four projects; the three FK-asserting tests were inverted, not deleted. Unblocks 0014, then 0015.

- [StagedIdentity on the durable store](tickets/0014-staged-identity-implementation.md) — **Built.** `StagedIdentity` is a GUIDv7 minted at seed creation; the negative integer is a persisted display alias. The ticket's open design question — where a durable identity lives when seeds are rows in the DROPPABLE `work_items` — resolves to a new durable `pending.staged_identities` table as the source of truth, with the mirror keeping a rebuildable convenience column. Two of 0003 §5a's constraints stop being prose and become structural: `alias` is UNIQUE but deliberately NOT the primary key and the table declares no FKs (asserted via `pragma_foreign_key_list`), and retirement is an UPDATE never a DELETE, so the row IS the retirement record and `MIN(alias)` cannot walk back over an issued number. Durable migration v2 is additive per 0013's rule (ALTER + backfill, tested against a pre-existing v1 store, not the create-at-v2 happy path). `publish_id_map` re-keys to the identity; `twig history` keeps ONE alias-shaped read that resolves through the register and returns null for an unknown alias rather than matching a neighbour (0003 §4). **The deletion test passed and found two live bugs:** `ISeedIdCounter`, `GetMinSeedIdAsync` and the #285 union query all deleted cleanly — and `NewCommand` (`twig new`) and `CreationTools` (MCP `twig_new`) were BOTH creating seeds without ever calling `Initialize`. 0003 §2's sixth-call-site argument was already true twice over, and neither site appeared in the handoff's verified file list because neither referenced the counter. Identity is now a required parameter, so a seventh site is a compile error rather than a silent collision. 7,389 → 7,379 tests, exit 0 on all four projects (net −10 accounted for: counter arithmetic deleted, six facts repurposed into StagedAlias/StagedIdentity properties, five schema guards added); two completeness guards fired as designed and their inventories were updated, not relaxed. Unblocks 0015.

- [The durable intent record](tickets/0015-durable-intent-record.md) — **Built, and the 7->10 window is closed.** The ticket's open question — what is the idempotency key — resolves to an **ADO tag**, and the three candidates were settled with the API in hand rather than in the abstract: ADO-side dedupe **does not exist** (no `clientRequestId`, no dedupe token, no conditional-create — verified absent, so push-and-recover is not a preference but the only option the API leaves); a custom field **would require changing the owner's ADO process template**, an organisational decision, so it was neither taken nor recommended; a tag needs no template change because tags are per-work-item DATA, not schema (`Create tag definition` is a default Contributor permission). **The sharper finding is that the tag must be a CONSTANT.** The first cut stamped `twig-intent:<GUIDv7>` — one unique tag per published item, which grows the project's unique-tag set without bound (ADO caps a project around 5,000) and writes twig's private bookkeeping into a namespace every human in the project sees in their tag picker. 0001 §1 already forbids that: the shared substrate is ADO, and twig owns only the pending set. Caught in review before merge. So the mechanism splits — the tag NARROWS, local state IDENTIFIES: `twig-publishing` is stamped on create and REMOVED once the publish is recorded (so the in-use set is bounded by what is actually in flight, normally one, and twig's permanent contribution to the shared vocabulary is ONE tag), while the intent row's `title`/`type_name`/`recorded_at` do the identifying via `System.CreatedDate >= recorded_at` — a sound fence precisely because `recorded_at` is written BEFORE the call, and never re-stamped while the intent is open. `publish_intents` is durable migration v3, additive per 0013, keyed on `StagedIdentity` per 0014, with `published_id IS NULL` as the reconcilable state — the SAME record 0003 §3 and 0004 §4 required, not a second one. Step 7 now records intent, **asks ADO whether the create already landed**, creates only if it did not, then records the outcome — all OUTSIDE the step-10 transaction, deliberately, since a record that rolled back with the local half would be erased by the exact crash it exists to survive. #270 therefore closes as a class: a crash in the window leaves an intent with no outcome, and the retry adopts the orphan instead of duplicating it. 0005 §4's ATTACH window is covered by the same record, with no separate machinery. **Review caught an ORDERING BUG that made the fix reintroduce the very defect it closes**, since corrected: the intent close and the tag strip both happened ~30 lines BEFORE the step-10 transaction began, so on the exact #270 rollback the retry found no tag (recovery could not narrow to the orphan) and no usable ledger row (`RecordIntentAsync` preserved a row only when `IsOpen`, so a COMPLETED intent fell through to `ON CONFLICT DO UPDATE`, resetting `published_id` to NULL and re-stamping `recorded_at` — destroying the evidence AND moving the fence past the orphan). `CreateAsync` fired again: DUPLICATE. It survived the first round because the ledger was WRITE-ONLY — `GetIntentAsync` had ZERO production callers, so no path exercised recovery-from-durable-state, and three tests were vacuous (one asserted the in-memory object built BEFORE the INSERT; the recovery test never issued a second `PublishAsync`). Fixed in three parts: strip the tag only AFTER the commit; preserve ANY existing intent, not just open ones; and READ THE LEDGER BACK before asking ADO — the read path it was built to serve and never had. Each guard proven non-vacuous by reverting each half independently and watching the named tests fail; the recovery test now drives a SECOND `PublishAsync` after a rolled-back first and asserts `CreateAsync` ran EXACTLY ONCE. **Also smoke-tested against live ADO, which caught a second real bug the mocks could not:** the first recovery clause was rejected outright — `HTTP 400, "You cannot supply a time with the date when running a query using date precision"` — which would have made the query silently return nothing, so the retry duplicates the item and #270 comes back THROUGH ITS OWN FIX. Resolved with `timePrecision=true` as a QUERY-STRING parameter (a body-level field is silently ignored; dropping the time degrades the fence to day granularity). Confirmed with positive and negative controls against a throwaway item, since created and deleted. 7,398 tests, exit 0 on all four projects; the regression tests were proven to FAIL at `e899de46` (the unfixed orchestrator calls `CreateAsync` unconditionally), and the timePrecision guard was proven non-vacuous by reverting the fix and watching it fail. Two follow-ons proposed, unassigned: drain open intents at startup, and honour `Retry-After`/429 on the publish path.

Cross-file transactions survive: measured, not assumed — `ATTACH` + one transaction spans both files and rolls back both under twig's WAL pragmas; only crash atomicity between the two commits is lost, a window strictly narrower than the ADO one #270 already falls through.
