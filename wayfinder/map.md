# Twig architecture — wayfinder map

## Destination
A twig codebase whose architecture matches its stated ideology — four experiences (rich CLI, script CLI, MCP-as-LLM-toolkit, TUI) over deep shared modules — with a persistence model chosen on evidence, and documentation that is true. Reached when every ticket below is closed and nothing structural is left to decide.

**Scope note (2026-07-26):** this map's destination is *decisions*, not shipped work. A
second map with the destination "twig 1.0 shipped" is chartered separately in issue #282
and deliberately deferred — a different destination means a NEW map, not a child of this
one. This map does not spawn sub-maps: work that cannot yet be phrased sharply belongs in
**Not yet specified** below and graduates into tickets as the frontier reaches it.

- VOCABULARY CHANGED (0001): `Workspace` is retired in favour of **Connection** (one {org}/{project} ADO endpoint) and **Bench** (a named, switchable set of work items). `Sprig` is RESERVED for a future planning-over-seeds mode. See `CONTEXT.md` §4.

## Decisions so far
<!-- one line per closed ticket -->
- 0008: all six registration touch points (3 CLI, 3 MCP) are now guarded by build-time completeness tests rather than by hand — including constructor-level assertions, because .NET DI's greediest-satisfiable-constructor rule makes a bare resolution test pass on a degraded path. The guards found a live bug: `twig save` was dispatching to an unregistered `SaveCommand`.

- [What is twig for?](tickets/0001-what-is-twig-for.md) — A single-user local tool each dev runs independently; the shared substrate is ADO, never twig. The cache is disposable, the PENDING SET is the only thing twig owns, and it needs its own lifecycle: selective push per item, forced parent-before-child sequencing, push-and-recover with durable intent recorded BEFORE the ADO call, interactive conflict resolution for humans and warn-and-advise for agents/scripts.

- [MCP toolkit scenarios and tool granularity](tickets/0012-mcp-toolkit-scenarios.md) — **MCP is FROZEN, not cut.** No new tools, no CLI↔MCP parity work; new agent capability goes through the script CLI first, and only a demonstrated scripting gap justifies a tool. Existing tools keep working. Backed by external evidence: the industry is actively leaving 1:1 proxying (GitHub 25→7 tools, Sentry advertises 9 of 48, Notion sunsetting its generated proxy), selection measurably degrades past 30–50 tools, and twig's 41 sit in that band. Scenario enumeration deferred with the evidence preserved.

- [Four surfaces, one seam?](tickets/0002-four-surfaces-one-seam.md) — **Three surfaces at one CAPABILITY seam, not four adapters at one render seam.** `Twig.RenderTree` has ONE adapter at the surface seam (its four renderers are `--format` values on the CLI) and is presentational, so it is scoped down to the CLI's format layer, not promoted. The real seam already exists and is already deep: the six mutation workflows in `Twig.Infrastructure/Services/Mutation/`, each with exactly two adapters (a CLI command and MCP's `MutationTools`), whose `Validate` → *(surface interjects if it can)* → `Execute` → match-the-outcome-union shape encodes INTERACTIVITY — the axis that actually varies. Reads never got it, and MCP's 34-property `WorkspaceContext` is the negative space where the read seam should be. Read workflows take ONE method, and REACH becomes an outcome case (`NotCached`), not a fetch policy buried in shared code — which puts the sync boundary back in the surface where 0001 §5 says the user owns it. Surfaces are counted by interaction model, not audience: CLI (experiences 1+2), TUI, MCP.
- [Seed identity model](tickets/0003-seed-identity-model.md) — **A seed's identity becomes a durable `StagedIdentity` minted at creation; the negative integer is demoted to a display alias.** Options (a) and (b) are rejected as a class: both are allocators, and every allocator needs a durable floor twig has nowhere to keep. (b) already shipped in #285, but it moved correctness onto the assumption that `publish_id_map` is permanent — and `DropAllTables` drops it on any `SchemaVersion` bump, while `init --force` deletes the DB, so #280 recurs through a different door. Per 0001 §1 that map is durable provenance sitting in the disposable mirror. The allocator also depends on five call sites each remembering to `Initialize` first — the `SaveCommand` failure shape from 0008. A generated identity has no preamble to forget: `ISeedIdCounter` and `GetMinSeedIdAsync` both delete cleanly, and the pre-ADO intent record 0001 §4 requires finally has a key that survives a cache wipe. Decision only; 0005 owns the schema work.
- [Does reconciliation exist?](tickets/0004-does-reconciliation-exist.md) — **Reconciliation becomes a named module owning staged → published → reconciled → invalidated.** Today the decision "when do local and remote meet" is nobody's: five independent opinions (`SyncCoordinator:51` staleness, `RefreshOrchestrator:74-91` plus an unguarded `force` bypass, `HydrateAncestorsAsync:104`, `PendingChangeFlusher:142-145`), the FK ordering rule enforced only by four XML doc comments, and `IPendingChangeStore?` nullable with legacy overloads at three sites — 0003's five-call-site argument at larger scale. `ConflictResolver:36` is already deep and simply unreachable from the paths that matter; the module exists to make it the default. **Unit is the pending set, per Connection — a Bench is a view, never a sync unit.** **Staleness-triggered fetch is removed, not relocated**: reads are cache-only and return `Stale(lastSyncedAt)` as an outcome each surface renders, per 0002's REACH-is-an-outcome ruling; `--no-refresh` is deleted and refresh becomes opt-in `--refresh`. The durable intent record is 0003's, keyed by `StagedIdentity` — not a second one. 0004 owns the root cause of #268/#269/#270/#271. Decision only; 0005 owns persistence, 0006 the baseline revision.

## Not yet specified
- Whether the TUI ships as its own product or as a mode of one binary. Partly clarified (owner, 2026-07-26): the TUI is a CLI *concept* — same user, same terminal, same mental model — but "can be its own product." That places it conceptually without deciding packaging, so whether `src/Twig.Tui` keeps its own composition root and output stack stays open. See tickets 0002 and 0007.
- **Is the pending set per-Bench or per-Connection?** Decides what "selective push" actually selects, and therefore what the reconciliation module owns. Sharp enough to be near-ticketable; held here only because it may be answered inside 0004.
- **Does a Bench scope the sync boundary, or only reads?** If a Bench is the unit of refresh, it interacts with the watermark polling strategy from 0001 §7.
- **Who owns the sync boundary when an LLM triggers a fetch?** 0001 §5 says the boundary must be explicit and user-owned; 0002 §b notes MCP can be asked about data twig has never cached. Those two are in tension and nothing currently resolves it.
- Migration sequencing: if both the persistence model and the surface seam change, which lands first and how the intermediate state stays shippable.
- Whether `docs/specs/` should remain hand-written prose or be generated from code once the surfaces share a seam.
- What twig's public contract actually is for external consumers, and what a breaking change means for it.
