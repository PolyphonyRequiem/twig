# Issue tracker

Twig development is tracked in **Azure DevOps `PolyphonyRequiem/Twig`** through
the current Twig CLI. GitHub is the public record, not an inferred work tracker.
Verify the intended connection before acting; a Git remote or recorded status
alone is not fresh access evidence.

Read `twig --version`, the relevant group/leaf help, and the bundled `twig`
skill. Current workspaces use fresh Core initialization. Do not copy old SQL
caches, invoke the removed plan seeder/context-switch script, or use `twig new`,
`plan` aliases or retired integration tools.

For machine operations, explicitly target work with `--id` and use complete
structured output. `set` is a human local pointer, never ownership or assignment.
Discover types, states, fields, allowed values and close gates from the connected
schema rather than assuming this board's template in generic code.

Inspect pending work before save/discard/sync. Follow the actual command's
staging/publication contract; neither a local write nor a zero exit code alone
proves a remote result. Use current v3 proposals, exact preview digests and the
Core journal, then refreshed readback.

For a gated close, carry the state and every required unsupplied gate field in
one batch operation. Never use a bare state transition that cannot carry its
required fields. Record meaningful checkpoints and do not mark tracked work
complete before the refreshed provider state proves closure.

Historical plans and maps may provide context; they do not authorize remote
creation, closure or replay. Follow the user's explicit scope.
