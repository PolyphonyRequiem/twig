# Twig architecture — wayfinder map

## Destination
A twig codebase whose architecture matches its stated ideology — four experiences (rich CLI, script CLI, MCP-as-LLM-toolkit, TUI) over deep shared modules — with a persistence model chosen on evidence, and documentation that is true. Reached when every ticket below is closed and nothing structural is left to decide.

**Scope note (2026-07-26):** this map's destination is *decisions*, not shipped work. A
second map with the destination "twig 1.0 shipped" is chartered separately in issue #282
and deliberately deferred — a different destination means a NEW map, not a child of this
one. This map does not spawn sub-maps: work that cannot yet be phrased sharply belongs in
**Not yet specified** below and graduates into tickets as the frontier reaches it.

## Notes
- Domain vocabulary: `CONTEXT.md` at repo root is authoritative for NAMES. Architecture vocabulary: the `codebase-design` skill (module, interface, depth, seam, adapter, leverage, locality; the deletion test; one adapter = hypothetical seam, two = real).
- Skills every session should consult: `codebase-design`, `grilling`, `decision-mapping`, `improve-codebase-architecture`.
- Evidence ledgers live in `%TEMP%\twig-review\`: ledger-specs.md, ledger-architecture.md (arch-a/arch-b), ledger-parity.md, candidates-surface.md, candidates-state.md, candidates-output.md. ~130 audited findings, all cited path:line.
- Twig has FOUR experiences and THREE composition roots (CLI, MCP, TUI). Only the CLI references Twig.RenderTree. The four experiences are defined in `CONTEXT.md` §4 and ticket 0002 — do not use the older "human/AI/toolchain/TUI" shorthand, which conflated audience with interaction model.
- VOCABULARY CHANGED (0001): `Workspace` is retired in favour of **Connection** (one {org}/{project} ADO endpoint) and **Bench** (a named, switchable set of work items). `Sprig` is RESERVED for a future planning-over-seeds mode. See `CONTEXT.md` §4.
- ADO API facts established by research (0001 §7, full findings in `%TEMP%\twig-review\research-ado-*.md`): no self-servable event source, so polling is structural; `reporting/workitemrevisions` + continuationToken is a clock-free watermark and beats the staleness clock; `$batch` is NOT atomic; creates have NO idempotency key, so push-and-recover is forced rather than chosen.
- This is a PLANNING map. Produce decisions, not deliverables. One ticket per session.
- Doc-rot (~110 mechanical corrections) is deliberately NOT in this map — see Out of scope.
- Ticket 0011 (startup + observability) carries the only measured latency numbers in this map. Any ticket arguing about the cost of work should cite it rather than assert.
- Ticket 0012 (MCP toolkit scenarios) carries the external evidence on MCP tool design — industry granularity convention, measured tool-count degradation, and an 18-scenario candidate list. Any ticket arguing about the MCP surface should cite it rather than assert.

## Decisions so far
<!-- one line per closed ticket -->
- 0008: all six registration touch points (3 CLI, 3 MCP) are now guarded by build-time completeness tests rather than by hand — including constructor-level assertions, because .NET DI's greediest-satisfiable-constructor rule makes a bare resolution test pass on a degraded path. The guards found a live bug: `twig save` was dispatching to an unregistered `SaveCommand`.

- [What is twig for?](tickets/0001-what-is-twig-for.md) — A single-user local tool each dev runs independently; the shared substrate is ADO, never twig. The cache is disposable, the PENDING SET is the only thing twig owns, and it needs its own lifecycle: selective push per item, forced parent-before-child sequencing, push-and-recover with durable intent recorded BEFORE the ADO call, interactive conflict resolution for humans and warn-and-advise for agents/scripts.

- [MCP toolkit scenarios and tool granularity](tickets/0012-mcp-toolkit-scenarios.md) — **MCP is FROZEN, not cut.** No new tools, no CLI↔MCP parity work; new agent capability goes through the script CLI first, and only a demonstrated scripting gap justifies a tool. Existing tools keep working. Backed by external evidence: the industry is actively leaving 1:1 proxying (GitHub 25→7 tools, Sentry advertises 9 of 48, Notion sunsetting its generated proxy), selection measurably degrades past 30–50 tools, and twig's 41 sit in that band. Scenario enumeration deferred with the evidence preserved.

- [Four surfaces, one seam?](tickets/0002-four-surfaces-one-seam.md) — **Three surfaces at one CAPABILITY seam, not four adapters at one render seam.** `Twig.RenderTree` has ONE adapter at the surface seam (its four renderers are `--format` values on the CLI) and is presentational, so it is scoped down to the CLI's format layer, not promoted. The real seam already exists and is already deep: the six mutation workflows in `Twig.Infrastructure/Services/Mutation/`, each with exactly two adapters (a CLI command and MCP's `MutationTools`), whose `Validate` → *(surface interjects if it can)* → `Execute` → match-the-outcome-union shape encodes INTERACTIVITY — the axis that actually varies. Reads never got it, and MCP's 34-property `WorkspaceContext` is the negative space where the read seam should be. Read workflows take ONE method, and REACH becomes an outcome case (`NotCached`), not a fetch policy buried in shared code — which puts the sync boundary back in the surface where 0001 §5 says the user owns it. Surfaces are counted by interaction model, not audience: CLI (experiences 1+2), TUI, MCP.
- [Seed identity model](tickets/0003-seed-identity-model.md) — **A seed's identity becomes a durable `StagedIdentity` minted at creation; the negative integer is demoted to a display alias.** Options (a) and (b) are rejected as a class: both are allocators, and every allocator needs a durable floor twig has nowhere to keep. (b) already shipped in #285, but it moved correctness onto the assumption that `publish_id_map` is permanent — and `DropAllTables` drops it on any `SchemaVersion` bump, while `init --force` deletes the DB, so #280 recurs through a different door. Per 0001 §1 that map is durable provenance sitting in the disposable mirror. The allocator also depends on five call sites each remembering to `Initialize` first — the `SaveCommand` failure shape from 0008. A generated identity has no preamble to forget: `ISeedIdCounter` and `GetMinSeedIdAsync` both delete cleanly, and the pre-ADO intent record 0001 §4 requires finally has a key that survives a cache wipe. Decision only; 0005 owns the schema work.
- [Does reconciliation exist?](tickets/0004-does-reconciliation-exist.md) — **Reconciliation becomes a named module owning staged → published → reconciled → invalidated.** Today the decision "when do local and remote meet" is nobody's: five independent opinions (`SyncCoordinator:51` staleness, `RefreshOrchestrator:74-91` plus an unguarded `force` bypass, `HydrateAncestorsAsync:104`, `PendingChangeFlusher:142-145`), the FK ordering rule enforced only by four XML doc comments, and `IPendingChangeStore?` nullable with legacy overloads at three sites — 0003's five-call-site argument at larger scale. `ConflictResolver:36` is already deep and simply unreachable from the paths that matter; the module exists to make it the default. **Unit is the pending set, per Connection — a Bench is a view, never a sync unit.** **Staleness-triggered fetch is removed, not relocated**: reads are cache-only and return `Stale(lastSyncedAt)` as an outcome each surface renders, per 0002's REACH-is-an-outcome ruling; `--no-refresh` is deleted and refresh becomes opt-in `--refresh`. The durable intent record is 0003's, keyed by `StagedIdentity` — not a second one. 0004 owns the root cause of #268/#269/#270/#271. Decision only; 0005 owns persistence, 0006 the baseline revision.

- [Split the store by durability class](tickets/0013-split-store-by-durability-class.md) — **Built.** `pending.db` is ATTACHed as schema `pending` and holds `pending_changes`, `publish_id_map` and `seed_links`; it is never dropped, and is versioned independently by `PRAGMA pending.user_version` over an additive migration ledger — twig's first migration path, and one it can never take back. `twig.db` keeps drop-and-recreate for what ADO can rebuild. The FK behind #268/#269/#270/#271 is now UNEXPRESSIBLE (two files cannot declare one), and #280 closes as a class since `publish_id_map` sits where a `SchemaVersion` bump cannot reach it. Two implementation facts later tickets depend on: SQLite resolves unqualified table names across attached schemas, so NO repository SQL changed; and the durable path is derived inside the constructor, so all three construction sites and ~60 test sites needed zero changes — there is no fourth place to forget. The clean-break guard found a live #271: `init --force` warned “pending changes will be lost” and deleted the DB anyway; it now refuses (exit 1) and never deletes `pending.db`. A second bug — an empty legacy `main.pending_changes` shadowing the durable table and silently taking the writes — was caught by an existing test and fixed. 7,383 → 7,389 tests, exit 0 on all four projects; the three FK-asserting tests were inverted, not deleted. Unblocks 0014, then 0015.


- [Persistence model](tickets/0005-persistence-model.md) — **Neither, as asked: the store splits by DURABILITY, not by document-vs-relational.** That axis is already settled by the code (~69/31 document-shaped access, `SELECT *` on every read, `fields_json` is a document in a cell, 0 JOINs / 0 CTEs / 0 views / 0 triggers), so "go document" would rename a behaviour twig already has. Files-on-disk is rejected: 7 of 12 assumptions break, and the 3 things relational genuinely earns are exactly the 3 needing the global index an indexer would have to rebuild — while `WorkItemExportFormat` is lossy by design (12 excluded system fields, no parent/dirty/seed/sync state), an editing view, not a persistence format. The binding constraint is 0001 §1: `twig.db` stays the **disposable mirror** (drop-and-recreate retained, now safe), and a sibling **`pending.db` becomes the durable store** — never dropped, real migrations, holding staged seeds, the pending set, `publish_id_map`, the intent record and **Benches**. The line is one test: **can ADO rebuild it?** The single FK — root cause of #268/#269/#270/#271 — **disappears by construction**, since two files cannot declare one between them. Cross-file transactions survive: measured, not assumed — `ATTACH` + one transaction spans both files and rolls back both under twig's WAL pragmas; only crash atomicity between the two commits is lost, a window strictly narrower than the ADO one #270 already falls through. Clean break on existing data (no migration), but `init` **must refuse** when the old pending set is non-empty. Also records the `SaveCommand` call, asked four times and written down nowhere: **keep the handler** (it has per-item/all-dirty scoping `twig sync` lacks), delete `twig save` once `twig sync <id>` exists. Decision only — implementation graduates to 0013 (split), 0014 (`StagedIdentity`), 0015 (intent record), in that forced order; `SaveBatchProtectedAsync` goes to 0006, which does not need the new store.

- [Toolchain output stability](tickets/0010-toolchain-output-stability.md) — **`jsonc` is a mistake: not a format, not a flag. Delete it. The contract is the ACCEPT-LIST, not the payload.** The real count is 70, and it is 70 of 70: every `-o` doc comment in `Program.cs` advertises `jsonc` (#281's "79" is a line count; `grep -o` says 80). The "one implementation" is not one either — `NoteCommand.cs:140,159` only list `jsonc` inside an or-pattern already containing `json`, so no branch anywhere makes it differ from `json`. It is not a gap, because `json-compact` — the format the name abbreviates — is itself a no-op: `RendererFactory.cs:44-46` maps `json`/`json-full`/`json-compact` to the same `JsonRenderer(indented: true)`, as its own doc comment concedes. Two files assert opposite falsehoods about it (`BatchCommand.cs:39,260,303` calls human output an intentional "documented quirk"; `WorkspaceCommand.cs:28,651` claims it projects through the seam — while `:489` omits it), which is what a propagated string looks like, not a design. Per 0001 (single-user, local) there is no version skew and therefore no published payload contract: field shape stays deliberately unpinned — zero schemas and zero golden tests is the CORRECT number, not a defect. Breaking = removing an accepted `-o` value, or changing which family (human vs machine) it resolves to; adding a field is not. **The actual defect is the silent catch-all** (`RendererFactory.cs:48`, `OutputFormatterFactory.cs:30`) that turns any typo into prose-with-exit-0 down a `jq` pipe. The one pin worth paying for: validate `-o` once against a single accept-list and exit non-zero on a miss — one list, one test. The 33 drifted `IsMachineFormat` copies (`RefreshCommand.cs:72`, `ShowCommand.cs:716`, `WorkspaceCommand.cs:489,492,495`) must read from that list, but collapsing them is 0002's seam work. Corrects the ticket: `PlainOutputFormatter` is load-bearing (ANSI stripping for `TERM=xterm-256color` CI), NOT absorbable. Follow-on is a deletion sweep plus one validation site.
- [Startup cost and observability](tickets/0011-startup-and-observability.md) — **The 5s spike is neither timeout the ticket named, and the tracing machinery should be deleted rather than extended.** Measured, not inferred: `ConfigureServices` is deferred by ConsoleAppFramework until after command routing, so the composition root never runs on `--help` at all; every registration in it is already lazy `AddSingleton(sp => ...)`; and `TelemetryClient` is inert unless two env vars are set, with its POST fire-and-forget anyway. The real cause is `CompanionStartup.RunFirstRunCheck()` at `Program.cs:31` — a blocking GitHub download on a **60s** budget running ABOVE the `--help`/`--version`/unknown-command fast-exit at `:122-156`. Reproduced under control at **6499ms** with a companion binary removed vs **128ms** steady, and the intermittency is the `.twig-version` marker being one-shot-per-version, not a cache expiry. Fix is ordering, not DI shape, and **0007 does NOT share it** (the code sits above the composition root). Budget: **<400ms local-only, <150ms and ZERO network for no-workspace commands** — asserted behaviourally, not by wall clock. `--profile` REJECTED as premature: 0004 and 0005 both closed on structural grounds, so the instrument would postdate its own justification. **`Twig.Domain/Diagnostics/` fails the deletion test** — 20 instrumented call sites and ZERO `ActivityListener` anywhere in `src/`, so every span is null and every tag discarded; the tests pass only by installing a listener the product never does. OpenTelemetry rejected on 0001 (single-user local tool: one ~150ms process has no distributed trace to correlate). `ITelemetryClient` KEPT — unused-but-reachable and opt-in dark, unlike the ActivitySource. Grafana/OTLP ruled **out of scope**. Produces two `type: task` follow-ons: the startup-ordering defect (a user-visible 6.5s `twig --help` after every upgrade) and the diagnostics deletion.

## Not yet specified
- Whether the TUI ships as its own product or as a mode of one binary. Partly clarified (owner, 2026-07-26): the TUI is a CLI *concept* — same user, same terminal, same mental model — but "can be its own product." That places it conceptually without deciding packaging, so whether `src/Twig.Tui` keeps its own composition root and output stack stays open. See tickets 0002 and 0007.
- **Is the pending set per-Bench or per-Connection?** Decides what "selective push" actually selects, and therefore what the reconciliation module owns. Sharp enough to be near-ticketable; held here only because it may be answered inside 0004.
- **Does a Bench scope the sync boundary, or only reads?** If a Bench is the unit of refresh, it interacts with the watermark polling strategy from 0001 §7.
- **Who owns the sync boundary when an LLM triggers a fetch?** 0001 §5 says the boundary must be explicit and user-owned; 0002 §b notes MCP can be asked about data twig has never cached. Those two are in tension and nothing currently resolves it.
- Migration sequencing: if both the persistence model and the surface seam change, which lands first and how the intermediate state stays shippable.
- **Work-item files as a rendered projection for LLM consumption.** 0005 rejected files-on-disk as *storage* but explicitly did not reject this: a generated, disposable file view carries none of the 7 broken assumptions because it stores nothing. Owner's caveat (2026-07-27) is the real design problem — a file dump is as likely to blow an LLM's context as to assist it, so the question is scoping and selection, not format. Sits nearer 0010 (output stability) than 0005.
- Whether `docs/specs/` should remain hand-written prose or be generated from code once the surfaces share a seam.
- What twig's public contract actually is for external consumers, and what a breaking change means for it.
