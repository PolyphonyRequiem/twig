# Hostable work-item detail projection — Wayfinder map

## Destination

A build-ready specification for a framework-neutral work-item detail projection, backed by a verified external-host prototype. The specification preserves ADO's server-authored form structure and Twig-owned appearance vocabulary, gives read-only hosts no persistence dependency, defines optional editing capabilities explicitly, and provides a concrete migration route for Twig TUI.

The map ends at the implementation handoff. Shipping the package and production migrations belong to the build that follows.

## Lineage

- **ADO 155 — Expose a hostable work-item detail projection** is the work tracker and source acceptance brief.
- **Twig 1.0 Wayfinder, server-driven TUI editor decision** (`wayfinder-1.0/map.md`, ticket 1003) is settled input: the server's page → section → group → control structure governs the editor; widgets remain host-owned.
- **Twig 1.0 form-layout acquisition work** (ticket 1004 and `FormLayout`) is settled input: all four ADO levels and their order are preserved; column collapse is a rendering decision.
- This is a sibling map. It does not extend the completed Bench work or reopen Twig's surface architecture.

## Notes

- Domain vocabulary: `CONTEXT.md` is authoritative for names.
- Governing rule: **structure and projection are shared; rendering, frame, focus, sizing, scrolling, and application lifecycle belong to the host.**
- The first concrete customer is Bonsai's caller-owned duplicate-review pane. Twig TUI is the second customer and must consume the same projection.
- A test that injects its own projection or renderer does not prove hostability. The external-host prototype must construct the real public API from a consumer project and paint it inside a caller-owned frame.
- Preserve source values. Long/rich values may expose summaries, but the projection cannot truncate or discard the full value.
- Skills: `wayfinder`, `grilling`, `decision-mapping`, `substrate-consumer-ui-integration`, `capability-gate-review`, `integration-seam-verification`.
- One ticket per session.

## Decisions so far

- **Destination and architecture boundary** — confirmed by Daniel on 2026-08-07: this work should be wayfound before implementation; it is a projection/capability seam, not a shared renderer.
- **Public package boundary is `Twig.Domain`** (ticket 0001, pinned at `173d1673`): it is already packable as `PolyphonyRequiem.Twig.Domain` with zero project and zero runtime package references, multi-targets `net10.0;net11.0`, is AOT-clean, and already owns `WorkItemSnapshot`/`WorkItemTypeAppearance`/`FormLayout`. The only required source change is promoting `FormLayout`+`LayoutPage`/`Section`/`Group`/`Control` from `internal` to `public` via `PublicAPI.Unshipped.txt`; `IFormLayoutProvider`, `AdoIterationService`, `IPendingChangeStore`-backed editing, `IconSet` glyphs, and `Twig.RenderTree` stay off the consumer contract.
- **No node-link graph rendering — trees and lists only.** Cut by Daniel on 2026-08-07 after reading `docs/research/console-graph-rendering-prior-art.md` and `docs/research/console-graph-glyphs-and-interaction.md`. The surveys' own top recommendation was not a graph picture: it was a spanning tree with per-row edge-kind markers plus `(*)`-style located back-references (the `cargo tree` pattern), with an edge list grouped by relation kind as the narrow/machine fallback. Relationship *data* is still projected; only node-link layout is refused. Supporting evidence: no mainstream TUI draws a general node-link graph (k9s, lazygit, dua, btop are trees/lists; Bazel exports DOT instead), the crossing glyph vocabulary caps at two line weights with no bridge/diagonal/rounded-tee junctions, and a crossing cell has one foreground colour so colour-encoded edge kinds are undrawable exactly at crossings.
  **Two constraints survive the cut and still bind ordinary trees:** (1) ADO relations are cyclic in the wild — mutual `Related` links are trivially a 2-cycle — and `Spectre.Console.Tree` throws `CircularTreeException`, so any relation-following traversal needs its own visited set emitting reference markers *before* data reaches the renderer; (2) box-drawing `U+2500..254B`/`U+2550..2573` are `East_Asian_Width=Ambiguous` (double-width under CJK-configured terminals) while adjacent dashes/stubs are Neutral, and `Spectre.Console`'s `Cell.cs` caches width in an `sbyte[]` indexed by UTF-16 code unit — so *every* codepoint above `U+FFFF` mismeasures, which generalises the known Nerd Font SPUA bug and also rules out Symbols for Legacy Computing (`U+1FB00..1FBEF`).
- **The detail document carries every fact and lets the host drop what it wants** (ticket 0002, pinned at `74e2d6a1`): the server's four levels unchanged; each field control resolves to one of **three** states — has a value / empty on the server / not carried by Twig — because `FieldImportFilter` excludes all eight core fields (`System.Title` among them), every boolean, and unlisted read-only fields, so a naive lookup silently blanks a large slice of every form; non-`custom` pages and contribution slots are carried flagged rather than filtered; long values carry the full source value **and** a Twig-computed short form so hosts do not each cut differently; `ReadOnly`/`Visible` and `ControlType` are reported verbatim with no closed widget enum; and `WorkItemTypeAppearance` travels **separately** from the document rather than inside it.
- **The external-host probe is a real, running consumer, and it lives in-repo as a sample** (ticket 0003, pinned at `5b6064c3`): `samples/Twig.DetailHost` references `Twig.Domain` and nothing else, targets GA `net10.0`, acquires **zero** transitive runtime packages, and paints a caller-owned pane with no `Twig.Infrastructure`, `Terminal.Gui`, or `Spectre.Console`. The projection shipped as `WorkItemDetailProjector.Project(FormLayout, WorkItemSnapshot, fieldDefinitions?)` — a pure function over values — and the five layout records were promoted `internal`→`public` with the surface change tracked as 222 `PublicAPI.Unshipped.txt` entries. A **test project was rejected**: `InternalsVisibleTo` covers every first-party test assembly, so a test would compile against internals and pass while proving nothing; a sibling Bonsai spike was rejected for putting the load-bearing evidence where this repo's CI cannot break it. The boundary is checked negatively, not asserted — touching `IFormLayoutProvider` from the sample fails with `CS0122 inaccessible due to its protection level`. 0002 §11's acceptance floor (all three field states, a non-`custom` page, a contribution control) is exercised **and self-enforcing**: the sample exits non-zero if any of it stops holding, so it cannot decay into a demo. `TWIG-VERDICT OVERALL: PASSED`.
- **Twig TUI is migrated onto the shared projection, and the absent-layout fallback is a LAYOUT rather than a field list** (ticket 0004, pinned at `25d9f59d`): `WorkItemFormView`'s ten hard-coded `TextField`s are gone; its constructor builds only chrome and every row is created inside `LoadDocument(WorkItemDetailDocument, WorkItem)` by walking pages → groups → controls, so server order and process-specific fields are read rather than remembered. The null-layout case is answered by `FallbackFormLayout.For(snapshot)`, which returns a `FormLayout` — both branches therefore end in the same `Project` call and the view cannot tell them apart, which is precisely what stops the degraded path becoming the second field-selection implementation this ticket exists to prevent. It cannot enumerate `WorkItemSnapshot.Fields` (all eight core fields are absent from it), so it emits the eight core fields in a stable Twig-authored order then every carried field, and names only fields Twig demonstrably carries so it never reports *not carried by Twig*. 🔴 **A `null` layout and an empty served layout stay distinct** — the latter is projected as-is into an empty form, because collapsing them would make an empty server form silently sprout Twig-authored rows. **Editability remained a TUI decision but field selection did not:** rows exist because the document has them, while typing is bounded by `EditableFieldRefs` (the three fields `IPendingChangeStore` persists), and `DetailControl.ReadOnly` is deliberately NOT wired to it, preserving 0002 §6's reported-never-enforced rule. The acceptance floor is `WorkItemFormViewDocumentWalkTests` (16 arms, structural + behavioural), red-green verified twice: two structural arms compiled and **failed** at the pre-fix SHA naming all nine widgets, and a deliberately reintroduced hard-coded row failed **7 of 16** arms including the empty-document floor. Incidental fix: Domain's `InternalsVisibleTo` named `Twig.Tui` but the assembly is `twig-tui`, so the grant had never applied.
- **Editing is a separately-acquired capability, and the sink that stores a change decides what may be changed** (ticket 0005, pinned at `76572ea6`): the document is unchanged and an editable host acquires a **separate capability object**, correlated to controls by field reference name — so a read-only host never learns it exists and there is **no null-means-read-only mode switch**. **Field mutability is declared by the caller-owned persistence sink, not by `DetailControl.ReadOnly`**, which stays reported-never-enforced (0002 §6/§11 and 0004's pin survive intact): ADO marks almost nothing read-only, so flag-as-authority would make nearly the whole form typable while Twig can persist three fields, and the surplus edits would be silently eaten at save. `EditableFieldRefs` therefore becomes a *consequence* of `IPendingChangeStore`'s declaration rather than a hard-coded list. **State transitions are filtered at offer time AND re-validated at entry**, both from `ProcessConfiguration`/`StateTransitionService` with no infrastructure — but 🔴 **both are advisory**: `StateTransitionExecutor` records that the real per-process graph needs process-admin permission, so Twig infers legality from standard templates and **the server stays final**. **A state move is its own change kind** carrying accompanying field changes — justified NOT by the wire (ADO patches `System.State` like any field) but by real multi-hop chaining, one PATCH per intermediate. **Each change carries the prior value** for diffing/confirm/undo, explicitly **not** as the concurrency check, which stays revision-based. **Conflicts retry once then report, with the remote values attached** so a review pane can resolve them while a terminal form need not. **The host supplies the sink**; Twig's is one implementation, not a privileged one — which closes the loop, since the sink's declaration is what makes controls editable. Standing obligation on 0006: two sinks must both be exercised or the seam is unproven.

## Not yet specified

- ~~How a missing or unsupported server layout degrades without returning to a permanent hard-coded field list.~~ **Decided at ticket 0004: a Twig-authored fallback `FormLayout`, not a field list, and not "nothing".** See Decisions. The two absent cases stay distinct — `null` (no layout served) routes to the fallback, an empty served layout is projected as-is into an empty form. What remains open is narrower and belongs to 0006: whether the fallback is part of the **public package** at all, since it is Twig's opinion about arrangement rather than the server's structure — closer in kind to `WorkItemTypeAppearance`, which 0002 §9 deliberately kept outside the document.
- **Sibling projection primitives beyond the form.** Confirmed by Daniel on 2026-08-07: the detail form is not the only projection a host wants. Two more are known: the **hierarchy tree** (parent/child, carried today as `WorkItem.ParentId` — a strict tree) and **relationships** (`WorkItemLink` with `LinkTypes.Related` / `Predecessor` / `Successor` — cycles and multiple paths legal in the data). Twig's own render vocabulary knows only the first: `RenderNode.TreeView`/`RenderTreeBranch` model a row with children and cannot express a non-hierarchy edge. **Ticket 0001's package boundary already covers all of them** — `Twig.Domain` has zero project and zero runtime package references regardless of which primitive ships on it, and `WorkItemLink` is already `public` there. Node-link graph *rendering* is now cut (see Decisions), so the remaining open question is narrower: what the tree projection carries so a host can render relationships as marked rows and grouped lists rather than as a picture. Out of scope for this map — chart separately; do not widen ticket 0002, which is form-shaped.
- ~~Whether the external-host prototype belongs in this repo as a sample, a test project, or a sibling Bonsai spike.~~ **Decided at ticket 0003: an in-repo sample, `samples/Twig.DetailHost`.** See Decisions.
- Package/API compatibility promises and versioning at the first external release. Sharpened by ticket 0001: the vehicle is `PolyphonyRequiem.Twig.Domain`'s existing `PublicAPI.Shipped.txt`/`Unshipped.txt` analyzer discipline, and the open part is now narrower — what compatibility promise attaches to the promoted layout types across `net10.0`/`net11.0`, and whether Domain's broad existing surface should be narrowed into a separate `Twig.Detail` package. **Ticket 0003 made the cost concrete rather than predicted:** the promotion plus the projection landed as 222 `PublicAPI.Unshipped.txt` entries, and a real consumer's IntelliSense now demonstrably carries all of Domain's ~30 interfaces alongside the five projection types — while its transitive runtime package list is empty. Surface bloat, confirmed; dependency contamination, ruled out. Decide at 0006. **Ticket 0004 added 8 more entries (230 total) and one new question:** whether `FallbackFormLayout` belongs on the public surface at all. Also inherited from 0003: whether Twig ships field definitions alongside the document, since without them an absent non-core field reports *not carried by Twig* rather than *empty on the server* — 0004's fallback sidesteps this by naming only carried fields, but the served-layout path is unaffected. **Ticket 0005 added the most weight yet to splitting:** the editing contract introduces a capability type, a change-proposal type and a caller-owned sink interface, and a read-only consumer's IntelliSense would otherwise carry an editing vocabulary it can never call — while 0003 already showed Domain's ~30 interfaces reaching a consumer that wanted five types. 0005 also leaves one shape for 0006 to settle — whether the conflict report (which must carry the remote revision's values) reuses `WorkItemDetailDocument` or a narrower carrier — and imposes one acceptance criterion: **two sinks must both be exercised**, since a single-implementation abstraction is not a proven seam.

## Out of scope

- A shared Terminal.Gui, Spectre.Console, ratatui, or other renderer.
- Node-link graph layout in a terminal — lane gutters, layered box diagrams, adjacency matrices, arc diagrams. Cut 2026-08-07; see Decisions. Trees and lists only.
- Ownership of any host's frame, focus, keyboard routing, dimensions, scrolling, navigation, or lifecycle.
- Making Bonsai a second ADO client or exposing Twig authentication/infrastructure to consumers.
- Rebuilding the whole Twig TUI session model; this map only defines migration of item-detail semantics.
- Publishing or shipping the final package. That is the implementation handoff after this map closes.
